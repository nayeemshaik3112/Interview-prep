## Group A: Idempotency (new code)
## "How do you prevent duplicate claims in your system?"

Three layers: First, the controller checks an X-Idempotency-Key header against the claim_view table before dispatching any command — duplicate requests return the existing claim with HTTP 200 instead of creating a new one. Second, the outbox handler uses a deterministic eventId and checks for its existence before inserting. Third, the notification consumer checks a notification_log table by eventId before processing. This gives end-to-end exactly-once semantics from HTTP entry all the way to notification delivery.
----------------------------------------------------------------------------------------
## "What if the idempotency key is not sent by the client?"

The header is required=false. If absent, the controller generates a random UUID as the key. This means backward compatibility is maintained — old clients still work, but they don't get deduplication protection since each request gets a fresh key. We log a warning to push clients to adopt the header.
----------------------------------------------------------------------------------------
## Group B: Axon
## "Why use Axon Framework for Claims?"

Claims have a complex lifecycle with 6+ state transitions, mandatory audit requirements, and multiple downstream consumers (notifications, reporting, eligibility). Axon gives us: full immutable event history out of the box, CQRS for independent read/write optimization, replay capability to rebuild projections without data migration, and a structured way to implement business rules via aggregates without building all that infrastructure ourselves.
----------------------------------------------------------------------------------------
## "What is the difference between @CommandHandler and @EventSourcingHandler?"

@CommandHandler is where business decisions live — it validates the command, can throw exceptions, and calls apply(). @EventSourcingHandler is where state assignment lives — no logic, no external calls, purely assigns field values. The separation is critical because @EventSourcingHandler runs both when events are first created AND when Axon reconstructs aggregate state by replaying past events. If business logic were there, it would re-execute during replay — breaking idempotency.
----------------------------------------------------------------------------------------
## "How does Axon rebuild aggregate state after restart?"

When a new command arrives for an existing aggregate, Axon queries the Event Store for all events with that aggregateId ordered by sequence number, then replays them one by one through the @EventSourcingHandler methods. The result is the aggregate in its current state — without touching any external DB. This is pure Event Sourcing: state is always derived from events.
----------------------------------------------------------------------------------------
## Group C: Kafka + Outbox
## "Why Outbox Pattern instead of publishing directly to Kafka from the EventHandler?"

MySQL and Kafka are two different external systems. You can't span a single ACID transaction across both. If you update MySQL and then call Kafka, a crash between the two leaves the system in an inconsistent state — domain state updated but notification never sent. The Outbox Pattern writes both the domain projection AND the outbox record to the SAME MySQL transaction. A separate scheduler then publishes the outbox records to Kafka with retry, backoff, and dead-letter handling — guaranteeing eventual delivery without risking silent data loss.
----------------------------------------------------------------------------------------
## "What is acks=all and why is it important?"

acks=all tells Kafka to wait for acknowledgment from ALL in-sync replicas before confirming the send. This is the strongest durability setting — even if the leader broker crashes immediately after the ack, the message exists on all replicas and won't be lost. For claim events (financial domain, audit-critical), losing a Kafka message is unacceptable, so we trade slightly higher latency for maximum durability.
----------------------------------------------------------------------------------------
## "How do you handle consumer rebalancing in your Notification Service?"

During rebalancing, partitions are temporarily unassigned. If a consumer was mid-processing when evicted, the new consumer re-receives those messages from the last committed offset — this is Kafka's at-least-once delivery. Our notification_log idempotency check ensures re-processing is safe: findByEventId() returns the existing log entry, duplicateCounter is incremented, and we return without resending — so no customer gets two notifications for the same event.
----------------------------------------------------------------------------------------
## Group D: System Design / Senior-Level
## "Your Read DB is eventually consistent with the Write side. How do you handle a user who queries immediately after creating a claim?"

Two approaches: First, for the HTTP response, the controller returns the claimId directly from the command result — not from a DB query. So the caller gets claimId + status immediately. For subsequent GET requests, the projection typically completes within 50–100ms via the EventBus, so in practice it's never noticeable. For strict read-after-write requirements, you could add a short polling/retry on the query side or return the full created object directly from the command response.
----------------------------------------------------------------------------------------
## "What would you improve in your system for production readiness?"

Three things: First, the Kafka cluster is single-broker with replicas=1 — a broker failure means total Kafka outage. I'd move to 3 brokers with replication factor 3 and min.insync.replicas=2. Second, Axon Server is running in standalone mode — a single point of failure for the event store. I'd use Axon Server cluster (3 nodes). Third, credentials are in plain-text application.yml — I'd use Kubernetes Secrets or HashiCorp Vault for secure config injection.
