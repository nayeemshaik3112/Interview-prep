## Q1. What is the difference between HashMap and ConcurrentHashMap? When would you use which?

"HashMap is not thread-safe — concurrent reads/writes cause ConcurrentModificationException or silent data corruption. ConcurrentHashMap uses segment-level locking (Java 7) and CAS + synchronized block on bin-level (Java 8+) — not a single lock on the whole map. This means multiple threads can read and write simultaneously without blocking each other unless they hit the same bucket.

In my IVR project, I used ConcurrentHashMap to maintain an in-memory idempotency cache across threads — where multiple Feign client threads were checking and updating request state concurrently. Using a plain HashMap there would have caused race conditions under load."

Follow-up 1: "Can ConcurrentHashMap guarantee consistency if you do a check-then-act operation?"
Answer: No — containsKey() + put() is not atomic. Use putIfAbsent() or computeIfAbsent() for atomic check-then-insert.

Follow-up 2: "What does computeIfAbsent() solve that putIfAbsent() doesn't?"
Answer: computeIfAbsent() only computes the value if the key is absent — lazy evaluation. putIfAbsent() always creates the value object first, even if the key already exists — wasteful for expensive object creation.

Follow-up 3: "What happens internally when two threads hit the same bucket in ConcurrentHashMap Java 8?"
Answer: One thread gets the synchronized lock on that specific bin node. The other waits. Only that bucket is locked — not the entire map.

## Explain Java Memory Model — Stack vs Heap, and what goes where.
Every thread gets its own Stack — it stores local variables, method call frames, and primitive values. The Heap is shared across all threads — it stores all object instances and class-level static data.
When I write Customer c = new Customer() — the reference c lives on the Stack of that thread. The actual Customer object lives on the Heap. If two threads hold references to the same object, they both point to the same Heap memory — which is why shared mutable objects need synchronization.

Garbage Collection happens on the Heap — divided into Young Generation (Eden + Survivor spaces) and Old Generation. Short-lived objects like DTOs created per request die in Young Gen after a Minor GC. Long-lived objects like Spring beans and caches migrate to Old Gen."

Real-world example: "In our microservice, each incoming HTTP request creates a RequestContext object. That object is short-lived — created, used, discarded per request. It lives and dies in Young Gen. Our Kafka consumer group registry is a long-lived Spring bean — it lives in Old Gen for the application's lifetime."

Follow-up 1: "What is a memory leak in Java if GC exists?"
Answer: Objects still referenced bu never used again — GC can't collect them. Common cause: static collections growing without bound, event listeners never deregistered, ThreadLocal not cleaned up.

Follow-up 2: "What is the difference between Minor GC and Major GC?"
Answer: Minor GC collects Young Gen — fast, frequent. Major (Full) GC collects Old Gen + Young Gen — slow, causes stop-the-world pause. High Full GC frequency = memory leak or undersized heap.

## What happens if you donot override equals and only override hashcode
If we override equals() but not hashCode(), equal objects may end up in different hash buckets. 
Since HashMap and HashSet first use hashCode to locate the bucket, equals() may never be called, leading to incorrect behavior.

## What happens if you use a mutable object as a HashMap key and modify it after inserting?

The object's hashCode will change after mutation. Now the HashMap will look for it in a different bucket than where it was stored. The entry is effectively lost — you cannot retrieve or remove it. The key is still in the map but unreachable. Best practice: only use immutable objects (Strings, Integer, Long, UUID) as HashMap keys.
