A. Creational patterns (2)
1. Factory Method / Factory Pattern
Definition (simple):
A factory hides new and decides which specific class to create based on input, instead of the caller doing new SmsSender() / new EmailSender() directly.

Where in your IVR project (could be used):
NotificationService could use a NotificationSenderFactory:

Input: channel (SMS, EMAIL, PUSH) from Communication Preference.
Output: correct sender implementation (SmsSender, EmailSender, PushSender).

This avoids if/else all over the code and makes adding new channels easy.

Interview Q&A:

Q: What is the Factory pattern and how would you use it in your IVR project?
A: Its a creational pattern that centralizes object creation behind a factory method.
In my IVR system, Id use a NotificationSenderFactory that returns SmsSender or EmailSender based on the users
communication preference, so the main code doesnt care which concrete class is used.

Tricky Q: How is Factory different from Strategy?
A: Factory decides which object to create; Strategy decides which behavior to execute on an alreadycreated object. 
Factory is about instantiation; Strategy is about selecting algorithms.

Builder

Builder helps construct complex objects step‑by‑step with readable methods, instead of using a huge constructor with 10 parameters.

Where in your IVR project:

You already use Lombok @Builder for things like ClaimCreatedEvent, ClaimEventOutbox, ClaimView, NotificationLog.

Those are perfect cases: many fields, but sometimes only some are set in certain contexts.

Interview Q&A:

Q: Where are you using the Builder pattern in your IVR system?
A: For domain objects with many fields like ClaimCreatedEvent and ClaimView. Using Lomboks @Builder, I can do ClaimCreatedEvent.builder().claimId(...).status("CREATED").build() instead of a long constructor, which keeps object creation readable and less error‑prone.

Tricky Q: When would Builder be overkill?
A: For simple objects with  3 fields, a normal constructor or static factory is enough. Builder makes sense when you have many optional fields or want fluent, readable construction.

Facade
Definition (simple):
Facade provides a simple interface on top of a complex subsystem.

Where in your IVR project:

IVR Orchestrator is effectively a Facade over multiple services:

It hides calls to Customer, Policy, Claims, Eligibility, Communication Preference.

Exposes a single endpoint /ivr/aggregate to the IVR/Twilio layer.

Interview Q&A:

Q: How does your IVR Orchestrator act as a Facade?
A: Instead of Twilio or the frontend calling five services separately, they call one endpoint in IVR Orchestrator. 
It internally orchestrates parallel calls to Customer, Claims, Policy, and Eligibility services and returns one aggregated response. 
So it hides complexity behind a clean interface.

Tricky Q: Whats the difference between Facade and API Gateway?
A: API Gateway is an infrastructure component at the edge (routing, auth, rate limiting for many services). 
Facade is an applicationlevel pattern inside your system that wraps complex logic behind a simpler API. In my project, API Gateway routes HTTP; IVR Orchestrator is the Facade.

4. Adapter
Definition (simple):
Adapter converts one interface into another that your code expects, so you can plug in third party or legacy APIs without changing your core code

In my backend, I use Adapter pattern when integrating with external services or different data formats. For example, I convert external policy service responses or 
Kafka messages into my internal DTOs, so my business logic remains clean and decoupled.
