## Synchronous

@FeignClient(name = "customer-service")
public interface CustomerClient {

    @GetMapping("/customers/{id}")
    CustomerDTO getCustomer(@PathVariable Long id);
}

@FeignClient(name = "policy-service")
public interface PolicyClient {

    @GetMapping("/policies/customer/{customerId}")
    List<PolicyDTO> getPolicies(Long customerId);
}

@Service
public class IvrAggregationService {

    @Autowired
    private CustomerClient customerClient;

    @Autowired
    private PolicyClient policyClient;

    public AggregatedResponse getCustomerDetails(Long customerId) {

        CustomerDTO customer = customerClient.getCustomer(customerId);   // 🔥 sync call
        List<PolicyDTO> policies = policyClient.getPolicies(customerId); // 🔥 sync call

        return new AggregatedResponse(customer, policies);
    }
}

## Asynchronous

@Service
public class ClaimService {

    @Autowired
    private KafkaTemplate<String, String> kafkaTemplate;

    public void createClaim(Claim claim) {

        // Save claim
        claimRepository.save(claim);

        // Publish event
        kafkaTemplate.send("claim-topic", "Claim Created for ID: " + claim.getId());
    }
}

@Component
public class NotificationConsumer {

    @KafkaListener(topics = "claim-topic", groupId = "notification-group")
    public void consume(String message) {

        System.out.println("Received: " + message);

        // Send SMS / Email
        sendNotification(message);
    }

    private void sendNotification(String msg) {
        System.out.println("Notification sent: " + msg);
    }
}

## Why microservices for a backend like insurance/IVR?
Because different parts of the domain change and scale at different speeds: Customer, Policy, Claims, Notification, Eligibility, IVR Orchestrator. 
Microservices let us deploy a change to Claims or Notification without touching Customer or Eligibility.
Each service owns its database and can scale independently — for example, Notification might need more instances than Policy if it processes more events. At the same time, we must handle distributed concerns: service discovery, centralized config, resilient communication, and observability.
-----------------------------------------------------------------   
## How do you decide service boundaries?

I start from business capabilities and real-world nouns: Customer, Policy, Claims, Notification, Eligibility, IVR Session. Each microservice owns a cohesive subset of the domain (bounded context) and its own data. I avoid splitting by technical layers (controller-service-repo as separate services) because that creates chatty, tightly coupled services. Instead, I aim for: “If I ask a business person to draw their org chart, my service names should look similar.”

Key patterns:

Saga pattern — orchestrate multi-step workflows via local transactions + compensating actions
Each service does its own DB work, and if something fails, we undo previous steps using compensating actions.

Outbox pattern — ensure data + outgoing event are updated atomically within a single service’s DB
Idempotency — ensure reprocessing the same event/request doesn’t break data

We avoid distributed ACID transactions across services and instead use eventual consistency with patterns like Saga and Outbox. Each service performs its local transaction, then publishes an event. Other services react to that event and update their own data.

## How do you maintain consistency across microservices without distributed transactions
For reliability, I use the Outbox pattern: when a service writes to its DB (e.g., a new claim), it also writes an event into an outbox table in the same transaction. A background process then reads the outbox table and publishes events to Kafka. This guarantees we never lose events even if Kafka is temporarily unavailable.
