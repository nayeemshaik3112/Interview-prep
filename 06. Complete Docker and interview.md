## 🔹 Definition

DEFINITION

Docker Swarm is Docker’s native orchestration tool used to manage and scale containers across multiple machines (nodes) as a cluster.

------------------------------------------------------------------

## 🔹 Architecture

ARCHITECTURE

Node Types:

Manager Node → Handles scheduling, cluster state, decisions
Worker Node → Executes containers
Service → Defines desired state (image, replicas, ports)
Task → Running instance of a container

------------------------------------------------------------------

## 🔹 Key Concepts

KEY CONCEPTS

Desired State → Swarm maintains defined replicas automatically
Self-Healing → Failed containers are restarted automatically
Load Balancing → Built-in routing to distribute traffic
Scaling → Increase/decrease replicas dynamically
Rolling Updates → Zero-downtime deployments
Overlay Network → Communication across nodes
Secrets → Secure storage of sensitive data

## How do you containerize a Spring Boot application?

Build the JAR with Maven/Gradle (mvn clean package).

Write a Dockerfile:
```dockerfile
FROM eclipse-temurin:17-jre-alpine
COPY target/myapp.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java","-jar","/app.jar"]
```

Build the image: docker build -t myapp:1.0 .

Run: docker run -p 8080:8080 myapp:1.0.

EXPOSE 8080 is documentation inside the image saying “this container listens on 8080”. It does not publish the port by itself.
-p 8080:8080 on docker run actually maps container port 8080 to host port 8080, so you can access it from outside.
------------------------------------------------------------------
## What is a Dockerfile? What is a base image?

A Dockerfile is a script with step-by-step instructions to build a Docker image — which base image to start from, how to copy the app, and what command to run.
The base image is the starting layer (e.g., eclipse-temurin:17-jre-alpine), which gives you a JRE and OS; you then add your app on top. Choosing a good base image affects size, security, and performance.

## profiles

Pass profile via env or cmd:
docker run -e "SPRING_PROFILES_ACTIVE=prod" myapp:1.0

Pass external config:

Mount a config directory: -v /config:/config and use spring.config.additional-location=/config/

Or use environment variables like SPRING_DATASOURCE_URL etc. — Spring Boot maps SPRING_DATASOURCE_URL to spring.datasource.url.
------------------------------------------------------------------
## What is a multi-stage build and why is it used

Multi-stage build uses separate build and runtime stages to keep the final image small and clean. You compile the app in a maven or JDK image, then copy only the final JAR into a smaller JRE image, so source code and build tools never end up in production image.

In my IVR backend, each microservice (Customer, Policy, Claims, Notification, IVR-Orchestrator, Config Server, Eureka, Kafka, Zipkin, Prometheus, Grafana) runs in its own Docker container. I have a docker-compose.yml that brings up:

All Spring Boot services

MySQL containers per domain service

Kafka + Zookeeper

Zipkin, Prometheus, Grafana for observability

Service-to-service communication uses service names as hostnames (claims-service, notification-service) inside the Docker network. Spring Boot picks up environment variables for DB URLs and Kafka bootstrap servers, and profiles like docker or prod can be activated via SPRING_PROFILES_ACTIVE in Compose. This setup lets me run the full microservice landscape with a single docker-compose up locally, very close to production behavior.

We used Spring Boot Buildpacks to containerize our microservices. Spring Boot Maven Plugin has a built-in build-image goal that uses Cloud Native Buildpacks internally.
