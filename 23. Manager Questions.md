Section A — Technical Questions Manager Style

## If two services stop communicating in production, what is your first step?

A: First I identify whether it is synchronous or asynchronous. For REST communication, I check Zipkin trace ID, Feign timeout, fallback logs, and circuit breaker state. For Kafka, I check consumer group lag, retry topic, dead letter topic, and whether the producer is publishing successfully.
WHY THIS WORKS: Shows structured debugging, not random restart behavior.

## One downstream service is slow. How do you protect the overall flow?

A: I use time limiter, circuit breaker, retry with small limits, and fallback response. In my architecture, the main flow should degrade gracefully instead of blocking all threads. I also monitor latency in Grafana and traces in Zipkin.
WHY THIS WORKS: Shows production-grade thinking and client impact awareness.

## Why did you use both REST and Kafka?

A: I used REST where the caller needed an immediate response, like fetching current data from a dependent service. I used Kafka where the action could happen asynchronously, like event processing between producer and consumer services. The trade-off is that Kafka adds retry, ordering, and DLQ handling.
WHY THIS WORKS: Shows decision-making, not tool-based answers.

## How do you handle duplicate requests?

A: I use idempotency keys or request IDs for operations that may be retried. The system checks whether the request was already processed and returns the previous result instead of creating duplicate data. This is important in distributed systems where retries are common.
WHY THIS WORKS: Shows awareness of real production failure patterns.

## Kafka message was produced but not consumed. What do you check?

A: I check topic name, consumer group, offset lag, serialization errors, retry topic, and dead letter topic. Then I verify whether the consumer application is running and whether the message schema matches the DTO. If needed, I replay from DLQ after fixing the issue.
WHY THIS WORKS: Shows practical Kafka troubleshooting.

## How do you know which service caused latency?

A: I use Zipkin distributed tracing to follow the request across services. Then I compare service-level latency in Prometheus/Grafana. If one Feign call or DB query is slow, the trace usually exposes the exact span.
WHY THIS WORKS: Shows observability-first debugging.

## How did you manage service configuration?

A: I used centralized configuration so service ports, database URLs, resilience settings, and environment-specific values are not hardcoded. This makes it easier to change config across environments without rebuilding every service.
WHY THIS WORKS: Matches JD requirement for configurable applications.

## What happens if Config Server is unavailable?

A: Existing running services continue with already loaded configuration. New services may fail to start depending on fail-fast settings. For production, I would keep config highly available and avoid making startup depend on a single instance.
WHY THIS WORKS: Shows operational maturity.

## How do you handle partial failure in microservices?

A: I avoid assuming all services will be healthy. I use fallback, retries, circuit breakers, timeout limits, and persistent request state. The goal is to return a controlled response instead of breaking the entire user journey.
WHY THIS WORKS: Shows resilience mindset.

## How do you secure APIs?

A: At minimum, I would secure entry through API Gateway using JWT validation, role-based access, and service-to-service trust. Internally, I would avoid exposing all services directly and would validate sensitive request fields.
WHY THIS WORKS: Shows security awareness without overclaiming.

## How do you scale one service without scaling all services?

A: Because services are independently deployable, I can scale only the high-load service replicas. For async consumers, I also check Kafka partitions and consumer group behavior before scaling. Scaling should follow metrics, not guesswork.
WHY THIS WORKS: Shows microservices scaling logic.

## What metrics do you monitor?

A: I monitor request rate, latency, error rate, JVM memory, circuit breaker state, Kafka lag, failed messages, and DB health. For business flows, I also track failed requests and duplicate/idempotent hits.
WHY THIS WORKS: Shows technical plus business observability.

## How do you avoid retry storms?

A: I keep retry count limited, add backoff, and combine retry with circuit breaker and timeout. I do not blindly retry non-recoverable errors like validation failures. Retry should protect the system, not overload it.
WHY THIS WORKS: Shows mature resilience understanding.

## How do you deploy this system locally or in lower environments?

A: I use Docker Compose to bring up infrastructure like database, Kafka, discovery, config, tracing, and monitoring. Each service has its own config and database. This helps reproduce integration issues before higher environments.
WHY THIS WORKS: Matches Docker and environment-management expectations.

## How do you debug memory issues?

A: I first check JVM memory graphs in Grafana, then logs for GC pressure or large payload handling. I also check whether streams or in-memory lists are processing too much data instead of pushing filtering to DB.
WHY THIS WORKS: Shows practical performance thinking.

## How do you handle API version changes between teams?

A: I avoid breaking existing consumers. I prefer backward-compatible DTO changes, versioned endpoints if needed, and contract discussion before implementation. For distributed systems, API change is a team decision, not just a code change.
WHY THIS WORKS: Shows cross-team maturity.

## What if the API Gateway is down?

A: Since gateway is the single entry point, external traffic will fail. I would check gateway health, route config, discovery registration, and logs. In production, gateway should run with multiple replicas behind a load balancer.
WHY THIS WORKS: Shows awareness of single point of failure.

## How do you recover failed async messages?

A: I check retry attempts and dead letter topic. After fixing the root cause, I replay messages carefully so duplicate processing does not happen. Consumer idempotency is important before replay.
WHY THIS WORKS: Shows safe recovery thinking.

## How do you decide if a failure should return fallback or fail fast?

A: If the user journey can continue with partial data, I return fallback. If correctness is critical, like creating a financial transaction, I fail fast and persist the failure. The decision depends on business risk.
WHY THIS WORKS: Shows business-based engineering judgment.

## How do you prove your architecture is lightweight?

A: Each service owns a clear responsibility, has its own database, communicates through REST or Kafka based on need, and can be deployed independently. I avoided heavy shared modules and kept configuration externalized.
WHY THIS WORKS: Directly matches “Microservices and Light Weight Architecture.”

Section B — Architecture & Design Questions

## Why microservices instead of monolith?
A: I chose microservices because different business capabilities needed independent ownership, database isolation, and independent scaling. The trade-off is operational complexity, so I added gateway, discovery, config, monitoring, and resilience.
WHY THIS WORKS: Shows balanced reasoning.

## Why database per service?
A: I used database per service to avoid tight coupling and allow each service to own its data model. The drawback is cross-service reporting and consistency become harder. I handle that using APIs, events, and clear ownership boundaries.
WHY THIS WORKS: Shows real microservices trade-off.

## How do you handle distributed transactions?
A: I avoid two-phase commit. For synchronous flows, I keep operations small and compensatable. For async flows, I use event-driven design, idempotency, retry, and DLQ handling to reach eventual consistency.
WHY THIS WORKS: Shows practical distributed-system thinking.

## Why API Gateway?
A: Gateway gives a single entry point, centralized routing, and a place to add cross-cutting concerns like authentication, rate limiting, and request logging. I do not put business logic in gateway.
WHY THIS WORKS: Shows proper gateway boundary.

## Why Eureka/service discovery?
A: Service discovery avoids hardcoding service locations and supports dynamic service registration. It is useful when services scale or move across environments. The trade-off is another infrastructure dependency.
WHY THIS WORKS: Shows infrastructure reasoning.

## Why CQRS in one service only?
A: I used CQRS where command and query needs were different and event history mattered. I did not apply it everywhere because it adds complexity. Simple CRUD services should remain simple.
WHY THIS WORKS: Shows restraint, not overengineering.

## Why event sourcing?
A: Event sourcing helps when state changes need auditability and replay. In my architecture, it fits lifecycle-style operations. The trade-off is projection consistency and more complex debugging.
WHY THIS WORKS: Shows depth and limitations.

## How would you achieve zero downtime deployment?
A: I would run multiple instances, use health checks, deploy one version at a time, keep backward-compatible APIs, and avoid breaking DB changes. Gateway/load balancer should route only to healthy instances.
WHY THIS WORKS: Shows deployment maturity.

## How do you choose sync vs async communication?
A: If the user needs an immediate answer, I use REST. If the work can happen later and should not block the user flow, I use Kafka. The decision depends on latency, consistency, and business criticality.
WHY THIS WORKS: Shows simple but strong decision logic.

## What is the biggest drawback of your architecture?
A: The biggest drawback is operational complexity: many services, databases, configs, traces, and failure points. I reduced the risk using Docker Compose locally, centralized config, observability, and resilience patterns.
WHY THIS WORKS: Shows honesty and ownership.

In my project, one improvement I owned was reducing duplicate processing in a distributed backend flow. The request came through an API entry point and triggered multiple downstream service calls and some asynchronous processing. During peak time, the upstream system sometimes retried the same request if the response was delayed. Functionally it was not always visible as a bug, but internally the same request was hitting downstream services multiple times, increasing database reads, latency, and infrastructure load.

I identified this through request logs, trace IDs, and monitoring dashboards. I proposed making the flow idempotent using a unique request identifier. If the same request was already completed, we returned the stored response instead of repeating the entire workflow. If the dependency was slow, fallback and timeout handling prevented the system from holding resources unnecessarily.

The reason I chose this approach was that it solved the problem without redesigning the whole architecture. It reduced duplicate downstream calls, improved stability, and helped reduce unnecessary processing cost by roughly 15-20% in retry-heavy scenarios. This was appreciated by the team, and I was nominated for an internal Wall of Fame recognition for taking ownership of a production efficiency issue.

Managerial Questions + Strong Answers

## Why did you choose idempotency as the solution?

Answer:
I chose idempotency because the issue was not that the business flow was wrong. The issue was that the same request was being executed multiple times due to retries. Idempotency allowed us to control duplicate execution without changing the full architecture. It was a low-risk improvement with direct impact on load, stability, and cost.
----------------------------------------------------------------------------------------------------
## What alternatives did you consider?

Answer:
We considered only increasing timeouts, but that would keep threads blocked for longer and could make peak load worse. We also considered scaling downstream services, but that would increase cost without fixing duplicate processing. Idempotency was better because it removed unnecessary work instead of adding more infrastructure.
----------------------------------------------------------------------------------------------------
## How did you identify this issue?

Answer:
I started with logs and trace IDs. I noticed the same type of request coming multiple times within a short window and triggering the same downstream calls repeatedly. Then I checked monitoring data and saw unnecessary repeated traffic during retry-heavy periods. That helped confirm it was a duplicate-processing issue.
----------------------------------------------------------------------------------------------------
## How did you measure the improvement?

Answer:
We compared request count versus actual unique request identifiers before and after the change. We also monitored downstream call volume, latency, failure count, and duplicate-hit count. After the change, duplicate requests were handled from stored results instead of repeating the full workflow.
----------------------------------------------------------------------------------------------------
## What was the business impact?

Answer:
The business impact was reduced unnecessary processing and more predictable response behavior. The system handled retry scenarios better, downstream services had less avoidable load, and support teams had fewer confusing duplicate logs to analyze. It also helped reduce compute and database usage for that flow.
----------------------------------------------------------------------------------------------------
## How did this save cost?

Answer:
Earlier, every retry triggered multiple downstream calls and database reads. After the improvement, duplicate requests were short-circuited and did not repeat the full workflow. In retry-heavy scenarios, we estimated around 15-20% reduction in avoidable processing for that flow, which directly reduced infrastructure pressure.
----------------------------------------------------------------------------------------------------
## How did you make sure the change was safe?

Answer:
We kept the change limited to request tracking and response reuse. We did not change the business calculation or downstream contracts. We tested normal requests, duplicate requests, failed requests, and slow dependency scenarios before rollout.
----------------------------------------------------------------------------------------------------
## What if the stored response was wrong?

Answer:
That was a valid risk. We only reused responses for successfully completed requests. Failed or incomplete requests were not blindly reused. Also, the stored response was linked to a unique request identifier, so we avoided mixing responses between different business requests.
----------------------------------------------------------------------------------------------------
## Did this affect scalability?

Answer:
Yes, positively. Instead of scaling all dependent services just to handle duplicate retries, we reduced repeated work at the entry flow itself. That means the same infrastructure could handle more real unique requests.
----------------------------------------------------------------------------------------------------
## How did you convince the team or lead?

Answer:
I did not present it as just a technical cleanup. I showed the repeated request pattern, downstream call impact, and how much avoidable work was happening. Once the team saw that we could reduce load without redesigning the system, the approach was accepted.
----------------------------------------------------------------------------------------------------
## What trade-off did you accept?

Answer:
The trade-off was that we added request-state storage and had to carefully manage completed, in-progress, and failed states. But that complexity was acceptable because it protected the system from duplicate execution and gave us better auditability
