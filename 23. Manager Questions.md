## Project Understanding

**Q: Explain your project architecture.**

**Answer:**
The system is a Digital Lending and Credit Ecosystem with 5 microservices:

| Service | Responsibility | Tech | Pattern |
|--------|--------------|------|--------|
| Loan Origination | Entry point | Spring Boot, Feign | CRUD |
| KYC Validation | External API | Resilience4j | Integration |
| Credit Engine | Risk analysis | Kafka | Async |
| Repayment Ledger | Transactions | CQRS | Event-driven |
| Reporting | Dashboards | Elasticsearch | Read-optimized |

Flow:
- Loan service → sync call to KYC  
- Heavy processing → Kafka  
- Ledger consumes events  
- Reporting uses Elasticsearch

## Decision-Based Questions

### Q: Why did you use CQRS instead of a single DB?

**Answer:**
CQRS was used due to read/write asymmetry:
- Ledger → heavy writes  
- Reporting → complex aggregations  

Using a single DB:
- Would degrade write performance due to indexing  

Solution:
- Write → PostgreSQL  
- Read → Elasticsearch  

Trade-off:
- Eventual consistency (200–500ms delay)

Mitigation:
- UI version check (“Processing” indicator)

---------------------------------------------------------------------------------------------------------------------

### Q: Why Kafka over REST or RabbitMQ?

**Answer:**
Kafka was chosen for:
- Decoupling services  
- High throughput  
- Log replay capability  

Key advantage:
- Replay events for audit/debug  

Example:
- Rebuild reporting system using past data  

Trade-off:
- Consumer lag  
- Partition management  

Handled via:
- Grafana monitoring

## Production & Failure Scenarios

### Q: What happens if KYC API becomes slow?

**Answer:**
Handled using Resilience4j Circuit Breaker

Config:
- failureRateThreshold = 50%  
- slowCallDuration = 2s  

Flow:
- Circuit opens → stops calls  
- Fallback triggered → Kafka queue  

Improvement:
- Reduced sliding window (100 → 10)  
- Faster failure detection  

Business impact:
- Prevents thread pool exhaustion  
- Keeps system responsive  

---------------------------------------------------------------------------------------------------------------------

### Q: Explain a Kafka production issue you handled.

**Answer:**
Problem:
- Poison message (missing field)  
- Consumer stuck retrying → partition blocked  

Impact:
- 2-hour delay  

Solution:
- Implemented Dead Letter Queue (DLT)  
- Retry with exponential backoff  

Flow:
- 3 retries → send to DLT → continue processing  

Result:
- MTTR reduced from 120 min → <5 min

## Cost Saving Story

### Q: Did you save cost for the client?

**Answer:**

Problem:
- High Kafka infra cost (~$35,000/month)  

Solution:
- Implemented Tiered Storage  
- Migrated to ARM-based instances  

Changes:
- 2 days data → EBS  
- 28 days → S3  

Optimization:
- Reduced storage cost  
- Improved CPU utilization  

Result:
- 65% cost reduction (~$22,000/month)  
- ~$250K yearly savings  

Business Impact:
- Budget reused for AI initiatives

## Deep Follow-Up Questions

### Q: Why Zstd over Snappy or Gzip?

**Answer:**
- Gzip → high compression but CPU heavy  
- Snappy → fast but low compression  
- Zstd → balanced (60% compression, low CPU)  

---------------------------------------------------------------------------------------------------------------------

### Q: Does Kafka decompress messages internally?

**Answer:**
No:
- Kafka stores compressed messages as-is  
- Decompression happens at consumer  

Benefit:
- Maintains zero-copy optimization  
- Keeps latency low  

---------------------------------------------------------------------------------------------------------------------

### Q: How did you validate performance improvement?

**Answer:**
- Used Canary deployment  
- Monitored p99 latency  

Observation:
- Slight latency increase initially  
- Improved network efficiency  

Result:
- p999 latency reduced from 2s → 400ms
